# Mehrsprachigkeit — Deutsch, Italienisch, Englisch, Tschechisch

Die Storefront läuft in vier Sprachen. Dieses Dokument beschreibt, wie das
System gebaut ist, was bereits übersetzt ist und wie eine noch deutsche Seite
nachgezogen wird.

---

## 1. URLs

Deutsch bleibt **ohne Präfix an der Wurzel**, die drei anderen Sprachen
bekommen eines:

| Sprache | Startseite | Beispiel |
|---|---|---|
| Deutsch | `/` | `/unsere-weine/lugana` |
| Italienisch | `/it` | `/it/unsere-weine/lugana` |
| Englisch | `/en` | `/en/unsere-weine/lugana` |
| Tschechisch | `/cs` | `/cs/unsere-weine/lugana` |

Der Grund ist Bestandsschutz: Die deutschen URLs sind seit 2019 indexiert.
Ein Umzug auf `/de/…` hätte jede davon weitergeleitet und das Ranking
zurückgesetzt. Die Pfad-Segmente selbst bleiben in allen Sprachen deutsch
(`/it/unsere-weine`, nicht `/it/i-nostri-vini`) — übersetzte Slugs wären ein
zweiter, unabhängiger Umbau.

`middleware.js` vermittelt:

- `/shop` → intern auf `/de/shop` umgeschrieben, die Adressleiste bleibt kurz
- `/de/shop` → **308** auf `/shop` (sonst wäre jede deutsche Seite doppelt erreichbar)
- `/` ohne Cookie → **307** nach Browsersprache auf `/it`, `/en` oder `/cs`
- Deep Links werden **nie** nach Sprache umgeleitet — ein geteilter Link führt
  immer exakt dorthin, wo er hinzeigt
- Die Wahl liegt danach im Cookie `mm_locale` (nur das Sprachkürzel, technisch
  notwendig, in der Datenschutzerklärung aufgeführt)

**Die gewählte Sprache bleibt, bis sie wieder gewechselt wird.** Zwei Stellen
sichern das zusammen:

1. Der Sprachumschalter schreibt das Cookie **selbst**, im Moment des Klicks
   (`components/i18n/LanguageSwitcher.jsx`). Er ist die einzige Stelle, an
   der ein Mensch seine Sprache wirklich *wählt*.
2. `remember()` in `middleware.js` überschreibt eine **abweichende**
   bestehende Wahl nicht mehr. Wer Italienisch gewählt hat und danach einem
   deutschen Deep Link folgt, sieht zwar die deutsche Seite (geteilte Links
   werden nie umgebogen), behält aber seine Sprache — der nächste Aufruf von
   `/` führt weiter nach `/it`.

Vorher schrieb die Middleware bei *jedem* Aufruf die Sprache der gerade
besuchten Seite ins Cookie. Ein einziger deutscher Link kippte damit die
Wahl dauerhaft zurück auf Deutsch.

**Die Sprachziele werden nicht vorab geladen, und Vorab-Ladungen lösen die
Sprachweiche nicht aus.** Beides zusammen behebt einen Fehler, der auf
Telefonen täglich auftrat: Auf `/it` zeigt der Umschalter für Deutsch auf
`/`. `next/link` holt dieses Ziel vorab (im Sichtfeld, bei Hover, bei
`touchstart` — also *vor* dem Klick), solange das Cookie noch `it` sagt, und
die Middleware antwortete darauf mit dem 307 nach `/it`. Der Router merkte
sich „`/` führt nach `/it`" und nahm beim Klick genau diesen Eintrag: Adresse
und Seite blieben italienisch, nur das Cookie stand auf `de`. Deshalb tragen
die Links im Umschalter `prefetch={false}`, und `middleware.js` behandelt
Anfragen mit `Next-Router-Prefetch: 1` unter `/` wie einen Deep Link — sie
bekommen die deutsche Wurzel, ohne Weiterleitung und ohne Cookie-Änderung.

**Crawler sind von der Sprachweiche ausgenommen.** Googlebot, Bing, die
KI-Crawler und die Vorschau-Dienste von WhatsApp, Slack & Co. bekommen unter
`/` immer die deutsche Startseite und nie eine Weiterleitung — sie halten
keine Cookies, für sie wäre also jeder Aufruf ein „erster Besuch". Ohne diese
Ausnahme hätte Google die deutsche Startseite womöglich nie als solche
gecrawlt: Erkennt es eine Umleitung nach `Accept-Language`, ruft es dieselbe
Adresse fortan mit wechselnden Sprachköpfen ab. Aus demselben Grund bekommen
Crawler **kein** `Set-Cookie` — der Kopf macht die Antwort für Vercels
Edge-Cache unspeicherbar, obwohl alle Seiten statisch vorliegen.

Das ist kein Cloaking: Crawler sehen exakt das, was auch ein Besucher ohne
Sprachpräferenz sieht. Alle vier Sprachen bleiben unter ihrer eigenen Adresse
erreichbar, in der Sitemap gelistet und über hreflang verbunden. Die Erkennung
steht als `CRAWLER` in `middleware.js`.

Ausgenommen vom Matcher: `/api`, `/admin`, `/_next`, `/img`, `/video`, `/fonts`
und alles mit Dateiendung.

## 2. Verzeichnisse

```
app/
  (site)/[locale]/     ← die gesamte Storefront, vier Sprachen
  (admin)/admin/       ← Backoffice, bewusst einsprachig deutsch
  api/                 ← einsprachig
content/
  de/ it/ en/ cs/      ← die Wörterbücher, gleicher Aufbau je Sprache
    weine-pages/       ← Text-Overlays der neun Weinseiten (nur it/en/cs)
lib/i18n/
  config.js            ← LOCALES, DEFAULT_LOCALE, Sprach-Metadaten
  routing.js           ← localePath / splitLocale / alternatePaths
  dictionaries.js      ← getDictionary(locale), nur Server
  context.jsx          ← I18nProvider + Hooks für Client-Components
  catalogue.js         ← Katalogstruktur + Sprache zusammenführen
  winePages.js         ← Weinseiten-Basis + Text-Overlay zusammenführen
  format.js            ← Preis, Zahl, Datum, Aufzählung je Sprache
  metadata.js          ← Titel, Description, hreflang, Canonical
components/i18n/
  LocaleLink.jsx       ← next/link, das die Sprache mitnimmt
  LanguageSwitcher.jsx ← Kopfzeile (Panel), mobiles Menü und Footer (Reihe)

Der Umschalter steht auf Telefonen **neben dem Menü-Knopf**, nicht darin: Wer
die Seite in der falschen Sprache öffnet, soll sie wechseln können, ohne erst
ein Menü zu suchen. Im mobilen Menü bleibt die flache Reihe zusätzlich
stehen. Die Pille trägt unterhalb `md` deshalb `h-11` (Höhe und Touch-Ziel des
Burgers) und ab `md` wieder `h-9` — die Desktop-Kopfzeile ist unverändert.
```

**Zwei Root-Layouts.** `app/(site)/[locale]/layout.jsx` und
`app/(admin)/layout.jsx` rendern jeweils eigene `<html>`/`<body>`. Nötig, weil
`<html lang>` die echte Dokumentsprache nennen muss und ein einzelnes
Root-Layout in `app/` die Locale nicht kennt. Sie über `headers()` zu holen
würde den ganzen Baum dynamisch machen und das Pre-Rendering kosten — so
bleiben alle 85 Seiten statisch.

## 3. Wie Text zu einer Komponente kommt

Drei Wege, bewusst getrennt:

| Fall | Weg |
|---|---|
| Server-Component | `const dict = await getDictionary(params.locale)` |
| Client-Component, gemeinsamer Rahmen | `useCommon("nav")`, `useCommon("cart")` … |
| Client-Component, seitenspezifisch | als Prop von der Server-Component |

Nur `content/<sprache>/common.js` reist über den Provider ins Browser-Bundle
(Navigation, Footer, Warenkorb, Katalogtext) — und immer nur **eine** Sprache.
Seitentexte gehen als Prop, sonst läge der komplette Redaktionstext in der
RSC-Payload jeder Seite.

`lib/i18n/dictionaries.js` wirft, wenn es im Browser landet.

## 4. Schlüssel statt Beschriftungen

Der Kern der Umstellung. Vorher war deutscher Text zugleich Datenschlüssel:

```js
WINES.filter((w) => w.type === "Rotwein")     // vorher
WINES.filter((w) => w.typeKey === "red")      // jetzt
```

`components/data.js` hält nur noch Struktur (`slug`, `price`, `year`,
`typeKey`, `regionKey`, `dot`, `photos`). Der sichtbare Text — „Rotwein",
„Apulien", Charakterworte, Speiseempfehlung — steht in
`content/<sprache>/common.js` unter `catalogue` und wird über
`lib/i18n/catalogue.js` beim Rendern dazugemischt.

Dasselbe gilt für die Anliegen im Kontaktformular (`tasting`, `merchant`,
`press`, `general`) und die Weinart-Filter. Query-Parameter bleiben unverändert
(`?art=rot`), damit bestehende Links weiter funktionieren.

`notes` ist eine **Liste**, kein Satz: Karten setzen die Worte mit „·"
getrennt, Fließtext braucht sie mit Konjunktion. `joinList()` in `format.js`
baut beides. Vorher zerlegte der Code den fertigen Satz am Wort „und" — was
außerhalb des Deutschen nichts findet.

## 5. Formatierung

`lib/i18n/format.js`, bewusst ohne `Intl`: Preise werden serverseitig
gerendert und im Browser rehydriert; weicht die ICU-Datenbank von Node auch
nur im Leerzeichen ab, meldet React einen Hydration-Mismatch.

| | Preis | Tausender | Datum |
|---|---|---|---|
| de | `16,90 €` | `18.000` | `4. Juli 2026` |
| it | `16,90 €` | `18.000` | `4 luglio 2026` |
| en | `€16.90` | `18,000` | `July 4, 2026` |
| cs | `16,90 €` | `18 000` | `4. července 2026` |

Die deutsche Ausgabe ist zeichengleich mit der Fassung vor der Umstellung.

## 6. SEO

`pageMetadata()` in `lib/i18n/metadata.js` erzeugt pro Seite und Sprache:

- Titel und Description aus `content/<sprache>/meta.js`
- `alternates.languages` mit allen vier Sprachen plus `x-default` → deutsche Fassung
- Canonical auf die eigene Sprachfassung
- OpenGraph mit `locale` und `alternateLocale`

Der Markenname kommt **einmal** aus dem `title.template` des Layouts. Mehrere
Seiten hängten ihn vorher selbst an, was zu „Unsere Weine — Maria Maria —
Maria Maria" führte.

## 6a. Die neun Weinseiten — Overlay statt Umbau

Die Produktseiten sind der einzige Bereich, der nicht dem Muster aus
Abschnitt 3 folgt. Ihre Daten liegen seit jeher in
`components/weine/<slug>/wineData.js` — rund 160 Strings je Wein, Struktur
und Text in einem Objekt, aus dem die Sektions-Components über ein einziges
`wine`-Prop lesen. Diese neun Dateien in Struktur und Text zu zerlegen hätte
jede von ihnen angefasst und damit die deutsche Fassung riskiert.

Stattdessen legt sich pro Sprache ein **Text-Overlay** darüber:

```
content/<sprache>/weine-pages/<slug>.js   ← nur die übersetzten Schlüssel
```

`lib/i18n/winePages.js` mischt beides beim Rendern zusammen
(`localizeWinePage`). Regeln des Merge:

- Strings ersetzen den Basiswert.
- **String-Listen** (`heroWords`, `paragraphs` …) ersetzen die Liste komplett.
- **Objekt-Listen** (`facts`, `taste`, `detail`, `faq`, `subnav` …) werden
  Position für Position gemerged: Das Overlay nennt je Eintrag nur die
  Textfelder, Icons/IDs/Bildpfade bleiben aus der Basis. Overlays müssen
  deshalb **dieselbe Reihenfolge und Länge** führen wie `wineData.js`.
- Für **Deutsch gibt es kein Overlay** — die Basis ist bereits die deutsche
  Fassung, der Merge ist dort ein No-op.
- Fehlt ein Schlüssel, bleibt der deutsche Text stehen. Das widerspricht
  bewusst der „lieber leer als deutsch"-Regel: Bei 160 Strings je Wein wäre
  ein leeres Loch mitten im Fließtext schlimmer als ein deutscher Satz.

Denselben Merge nutzt `lib/seo/wine.js` — sonst trügen Datenblatt und FAQ im
JSON-LD deutschen Text, während die Seite darüber übersetzt rendert.

Ein neuer Wein braucht also: `wineData.js` (deutsch), einen Registry-Eintrag
und drei Overlays. Ein neues Textfeld braucht denselben Schlüssel in allen
drei Overlays.

## 7. Stand der Übersetzung

**Vollständig in allen vier Sprachen:**

- Kopfzeile, Navigation, Wein-Dropdown, mobiles Menü
- Footer inklusive Newsletter-Block und Rechtslinks
- Sprachumschalter (Kopfzeile, mobiles Menü, Footer)
- Warenkorb — alle Zustände: leer, gefüllt, Versandschwelle, Bestellabschluss
- Weinkatalog: Weinarten, Regionen, Charakterworte, Speiseempfehlungen
- Kollektions-Filter (`/unsere-weine`) inklusive Leerzustand und Zähler
- Shop-Karten (Badges, limitierte Auflage, Knappheit) und Probierpakete
- Kontaktseite **und Kontaktformular** (Labels, Platzhalter, Validierung,
  Auswahlwerte, Bestätigung)
- Rechtstexte: Impressum, Datenschutzerklärung, AGB — mit sichtbarem Hinweis,
  dass die deutsche Fassung die rechtlich verbindliche ist
- Fehlerseite und 404
- Seitentitel, Descriptions, hreflang, Canonicals für **alle** Seiten
- Zahlen-, Preis- und Datumsformate
- Startseite, Shop, Kollektion (`content/<sprache>/home.js`, `shop.js`, `weine.js`)
- Geschichte, Regionen, Magazin (`geschichte.js`, `regionen.js`, `magazin.js`)
- **Die neun Weinseiten** über die Overlays aus Abschnitt 6a
- Beschreibung der Organisation im JSON-LD (`meta.orgDescription`)

Damit trägt keine Seite der Storefront mehr deutschen Fließtext in einer
anderen Sprachfassung.

**Bewusst unübersetzt — in jeder Sprache identisch:**

- Marken- und Produktnamen: „Maria Maria", „Il piacere del vino",
  „Enoteca Maria Maria", „Share the pleasure.", die Paketnamen
- Wein- und Rebsortennamen, D.O.C./D.O.C.G./I.G.P./DOP
- Italienische Gerichtsnamen der Food-Pairings (Spaghetti alle Vongole …)
- Die Rivista-Worte des Magazins: „Capitolo", „Bacheca", „Curiosità",
  „Interviste", „Archivio del Magazin", „Le occasioni", „Le Origini",
  „Cover Story", „Maria Maria Magazin"
- Namen von Personen, Künstlern und Orten (Salento, Lizzano, Torricella …)
- Die Ziffern in Produktnamen: „Primitivo 14,5" bleibt in jeder Sprache so

## 8. Eine Seite nachziehen

Am Beispiel `/regionen`:

1. **`content/de/regionen.js` anlegen** und den deutschen Text aus der Seite
   dorthin verschieben. Struktur (Reihenfolge, Icons, Farben, Bild-Pfade)
   bleibt im Code — ins Wörterbuch gehört nur Text.
2. **In `content/de/index.js` registrieren:**
   ```js
   import regionen from "./regionen";
   const dictionary = { common, meta, legal, kontakt, regionen };
   ```
3. **Die Seite umstellen:**
   ```js
   export default async function RegionenPage({ params }) {
     const dict = await getDictionary(params.locale);
     const t = dict.regionen;
     …
   }
   ```
   Client-Components darunter bekommen ihren Teil als Prop.
4. **`it`, `en`, `cs` anlegen** — gleiche Schlüssel, übersetzter Text, und in
   den jeweiligen `index.js` registrieren.
5. **Bauen und prüfen:** `npm run build`, dann alle vier Sprachfassungen
   ansehen.

### Regeln

- **Kein stiller Rückfall auf Deutsch.** Fehlt ein Schlüssel, bleibt die
  Stelle leer statt heimlich deutsch zu erscheinen — sonst bleibt eine Lücke
  monatelang unbemerkt.
- **Marken- und Produktnamen bleiben stehen:** „Maria Maria", „Il piacere del
  vino", „Primitivo di Manduria D.O.C.", „Trio Rosso", D.O.C./D.O.C.G./I.G.P.
- **Nie auf sichtbaren Text vergleichen.** Schlüssel für Logik, Wörterbuch für
  Anzeige.
- **Platzhalter statt Verkettung:** `"Noch {amount} bis zum kostenfreien
  Versand"` — die Wortstellung ist je Sprache anders.
- **Alle vier Dateien im selben Schritt ändern.** Besonders bei den
  Rechtstexten: eine veraltete übersetzte Widerrufsbelehrung ist schlimmer als
  gar keine.
- **aria-Labels nicht vergessen.** Sie sind der Teil, an dem eine halbe
  Übersetzung am deutlichsten auffällt.

## 9. Eine Sprache hinzufügen

1. `LOCALES` und `LOCALE_META` in `lib/i18n/config.js` ergänzen
2. `content/<sprache>/` als Kopie von `content/de/` anlegen und übersetzen
3. Zweig in `DICTIONARIES` in `lib/i18n/dictionaries.js` eintragen
4. Preis-, Tausender- und Monatsregeln in `lib/i18n/format.js` ergänzen

Routing, Sprachumschalter, hreflang und `generateStaticParams` ziehen
automatisch nach.
